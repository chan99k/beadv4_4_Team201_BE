# 동시성 경합 시나리오 실행 기록 (2026-10-01)

100 VU 가 서로 다른 사용자로 같은 펀딩에 동시 참여했을 때 정합성이 지켜지는지 확인한 기록.
산출물은 같은 디렉터리의 `concurrency-20261001-233850.json`.

멱등성 시나리오(`idempotency-20261001-233509.md`)와 짝이다. 그쪽은 **같은 키**로 보내
중복을 막는지 보고, 이쪽은 **다른 사용자**가 같은 자원에 몰릴 때 데이터가 깨지는지 본다.

## 실행 조건

```
funding 1002   current_amount 0 / target_amount 100,000 / IN_PROGRESS
product 14     stock 50
사용자         mockAuthHeaders(1001 + (__VU % 100)) -> member 1001~1100 (110명 시드됨)
executor       shared-iterations, 100 VU x 1 iteration
```

주의: 스크립트 헤더 주석이 낡아 `TEST_PRODUCT_ID` 가 빠져 있다. 실제로는 네 개가 모두 필요하다.
`TEST_FUNDING_ID`, `TEST_WISHLIST_ITEM_ID`, `TEST_RECEIVER_ID`, `TEST_PRODUCT_ID`.

## 결과 — 정합성은 지켜졌다

```
funding 1002   current_amount 11,000 <= target_amount 100,000      초과 없음
product 14     stock 50 >= 0                                        음수 없음
참여 행 수      11
고유 참여자 수   11                                                  중복 참여 없음
금액 합계       11,000  = current_amount 와 일치
orders 증가분   11      = 성공 건수와 일치
```

**세 가지 검증 목표를 모두 통과했다.** 펀딩 초과 없음, 재고 음수 없음, 중복 참여 없음.
성공한 11건과 참여 행 11건과 주문 11건과 금액 합계가 전부 맞아떨어진다. 경합 상황에서
부분 반영이나 유령 행이 생기지 않았다.

## 그러나 임계값은 깨졌다 — 그게 이 실행의 진짜 소득이다

```
http_req_failed   89.00%   (임계값 < 5%)        깨짐
error_rate        89.00%   (임계값 < 10%)       깨짐   status >= 500 기준
checks            11 / 100                      200, 201, 400 만 통과로 침
p95               715.92ms (임계값 < 1000ms)    통과
```

89건이 **4xx 가 아니라 5xx** 로 떨어졌다. 앱 로그에서 원인을 찾았다.

```
org.hibernate.StaleObjectStateException
  Unexpected row count (expected row count 1 but was 0)
  [update g7app.fundings set ... current_amount=? ...]
```

`fundings` 행에 걸린 **낙관적 락(optimistic lock)이 버전 충돌을 일으켰고, 그 예외가
그대로 500 으로 나갔다.** 100명이 같은 행을 동시에 갱신하니 거의 전부가 충돌한 것이다.

### 이게 왜 중요한가

정합성 자체는 낙관적 락이 지켜줬다. 데이터는 안 깨졌다. 문제는 **실패를 다루는 방식**이다.

```
지금    경합 -> StaleObjectStateException -> 500 Internal Server Error
        클라이언트 입장에서 "서버가 고장났다" 와 구분되지 않는다
        재시도해도 되는지 알 수 없다

되어야  경합 -> 짧은 백오프 후 재시도 (서버 쪽)
        그래도 실패하면 409 Conflict 와 Retry-After
        -> 클라이언트가 재시도 가능한 실패임을 알 수 있다
```

테스트의 check 가 `200 || 201 || 400` 을 통과로 보고 있다는 점도 같이 짚어둘 만하다.
**의도된 거절(400)과 서버 오류(500)를 가르는 기준은 들어 있는데, 구현이 그 기준을 못 맞춘다.**
테스트가 명세 역할을 하고 있고 구현이 거기 못 미치는 상태다.

## 후속 (미실행)

```
1  펀딩 참여 경로에 낙관적 락 재시도를 넣는다 (@Retryable 또는 수동 백오프)
2  재시도 소진 시 500 이 아니라 409 + Retry-After 로 응답한다
3  같은 시나리오를 다시 돌려 http_req_failed 가 임계값 아래로 내려가는지 본다
4  경합이 심한 자원에 비관적 락이나 큐잉이 맞는지 따로 판단한다
   (현재 11/100 성공률은 "안전하지만 처리량이 낮다" 는 뜻이기도 하다)
```
